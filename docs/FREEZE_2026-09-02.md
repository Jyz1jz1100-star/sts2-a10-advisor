# Freeze record — 2026-09-02 (Combat Solver pivot)

## Decision

The project pivots in-combat candidate generation to the external
**Combat Solver** mod (Slay the Spire 2 workshop item 3790899961, author
Torch123, requires RitsuLib 0.5.13+, game v0.111.0 — the locked build).
Two work streams are **frozen, not deleted**:

| Stream | Freeze marker | State at freeze |
| --- | --- | --- |
| Teacher v3 (beam teacher + long rollouts) | `data/teacher/FREEZE-TEACHER-V3.txt` | strength gate `expert_labels_approved: false` (bounded teacher, n=4); all records stay `label_status: "candidate"` |
| Combat PPO expansion (V2 curriculum ladder, floor6 ablation, pretrain-init screening) | `runs/curriculum_v2/FREEZE-PPO-EXPANSION.txt` | floor3 + floor6 promoted with hash-chained evidence; floor10 stalled by reward exploitation and stopped |

Nothing under `runs/`, `data/teacher/`, `models/`, or `checkpoints/` is
modified or removed by this pivot. The R2 freeze (`data/teacher/FREEZE-R2.txt`)
stays in force on top of the new marker.

## What stays active (unchanged)

- state recording: `bridge.trace_controller` JSONL traces + `decision_id`
  (normalized SHA-256 of raw state);
- version lock: `config/live_version.lock.json` (game build 24724944 /
  v0.111.0, STS2MCP 0.4.0 DLL+manifest hashes, mod whitelist);
- win-rate statistics: `training/wilson.py` + metrics schema;
- out-of-combat decisions: unchanged (no Combat Solver involvement — it is
  combat-only by design);
- the 500-run real-machine verification protocol: `docs/ACCEPTANCE.md`
  gates, seed partitions, and the `allowed_mod_ids` contamination guard.

## The new track

`docs/COMBAT_SOLVER.md` defines the phased plan:

1. **Phase A — structured read-only interface.** A file-based bridge that
   yields state hash, route JSON, search budget, and candidate routes from
   the solver's own on-disk outputs (no UI scraping, no memory reading, no
   POST to the game). A separate mod-environment lock
   (`config/combat_solver.lock.json`) records the additional mods so the
   A10 acceptance track's whitelist stays intact.
2. **Phase B — independent comparison.** 50–100 fixed battles comparing
   predicted vs actual HP loss, route deviation rate, solve time, memory,
   and failure rate, with pre-registered gates before any adoption.
3. **Phase C — adoption as in-combat candidate upper module** (only if
   Phase B passes): Combat Solver routes become the in-combat candidate
   source; the existing advisor keeps out-of-combat decisions.
4. **Phase D — distillation.** Low-latency combat policy distilled from
   accepted Combat Solver routes; hard battles may still call the original
   searcher. Teacher v3 stays frozen unless this phase reopens it.

## Explicit non-goals for this pivot

- No new PPO budgets, no teacher batch expansion, no BC retrains during
  Phases A–B.
- The Combat Solver track never writes to the game (read-only posture is
  inherited from the bridge: `bridge/client.py` has no POST path; the
  comparison harness must not use the solver's "execute/auto" modes for
  *evaluation* records unless that run is tagged `automated=true`).
