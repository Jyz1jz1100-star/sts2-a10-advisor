# Incident: deterministic evaluation infinite loop (2026-09-01)

Run: `runs/supervised-act1/20260831T163117Z` (act1 stage, MaskablePPO, 100M budget).
Detected by the unattended goal watch; trainer was killed before the fix and the
stage relaunched (`20260831T205351Z`) with guards.

## Symptom

The first checkpoint (`step_000002000004.zip`, saved 00:58:47) triggered its
100-episode checkpoint-split evaluation. After ~3.5 hours the evaluation had
produced no metrics; the process remained pinned at ~0.95 CPU core. The earlier
"evaluation is structurally slow (~2.5h)" interpretation was wrong.

## Root cause

- `py-spy dump --locals` on the live process (full capture saved to
  `.tools/diagnostics/eval_hang_dump_2026-09-01.txt`) showed `evaluate_policy`
  stuck on episode 44/100, `seed=20000043`, with `steps=9,170,993` and
  `total_reward=-9,170,958` (exactly −1.0/step), `illegal_actions=0`.
- The simulator's `Sts2RunEnv.step` returns
  `run_env._invalid_action() → (obs, -1.0, False, False, info)` when the native
  `run_step` rejects a move — it bypasses the Python-side `elapsed_steps` cap.
- The action *was* inside `action_masks()`, so `training/evaluation.py`'s own
  mask check passed; the loop trusted only the env's
  terminated/truncated signals → infinite spin on any state where the mask
  and the native engine disagree.
- Proof it is a hang, not slowness: a fresh process replaying the identical
  checkpoint + seeds (`scripts/probe_eval_breakdown.py`) completes ~90-step
  episodes in ~0.4 s each; the live loop was doing ~9M steps in one episode
  at ~1.3 s/step.

## Fix (committed with this note)

1. `training/evaluation.py`: `max_steps_per_episode` parameter; the episode
   loop truncates on its own counter and never trusts env signals alone.
   All call sites (`curriculum.py` ×3, `evaluate_checkpoint.py`) now pass the
   stage's configured `max_episode_steps`.
2. `training/curriculum.py`: the training worker wrapper applies the same
   external per-episode cap so a mask/native disagreement cannot poison a
   rollout stream either.
3. Regression test: `tests/test_training.py::EvaluationTests::
   test_external_step_cap_breaks_native_rejection_loop` (an env that always
   returns -1 / never terminates is truncated at the cap).
4. Verification on the real hang seed:
   `scripts/verify_eval_guard.py` → `steps=1200 truncation_rate=1.0 in 5.5s`.

## Impact accounting

- Run `20260831T163117Z`: aborted, no metrics emitted; checkpoint retained for
  forensics only. The aborted reason is recorded in its manifest.
- Such seeds are now visible as truncated episodes and are counted by the
  promotion gate's `max_truncation_rate` — a policy that triggers the
  mask/native disagreement cannot be promoted, which is the designed behavior.

## Root-cause reproduction (same day, `scripts/repro_mask_disagreement.py`)

Replaying the exact checkpoint and seed in a fresh process pinpoints the
disagreement precisely:

- episode 20000043, **step 33, floor 5, `phase=event`, `event_id=31`**
  (`neow_options=(0,0,0)`, hp 60/80);
- `action_masks()` reports `[0, 1, 2, 3]` legal;
- probing all four on the re-derived state: **action `0` is rejected
  (`reward=-1`, phase stays `event`), actions `1`, `2`, `3` are accepted**.

So this is a genuine mask/native bug in the simulator for one specific event:
the mask marks an event option legal that the native `run_step` refuses. Why
training survived but evaluation hung: training rollouts sample stochastically
and escape by eventually picking 1/2/3, whereas deterministic evaluation keeps
picking argmax action `0` forever at ~1.3 s/step — the 9.17M-step hang.

Consequences to keep in view during the parity phase (not yet acted on):
- Any greedy policy that prefers option 0 at `event_id=31` will show up as a
  truncated episode in deterministic evaluation, inflating `truncation_rate`
  and potentially blocking promotion for reasons unrelated to play strength.
  The promotion gate therefore stays conservative-by-construction here.
- A cleaner future metric split is a separate "native-rejection / no-progress"
  counter distinct from genuine length truncation; deferred so live metrics
  keep one schema version.
- The bug itself is in the MIT-licensed third-party emulator; reproduction is
  now a concrete upstream/parity work item: reconcile event option indexing
  for `event_id=31` between the mask builder and the C# `run_step` dispatcher.
